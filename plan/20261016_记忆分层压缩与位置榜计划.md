## 1. 已确认的决策

| 决策点 | 结论 |
| --- | --- |
| 300 / 100 口径 | **全局**条目总数；白天的自动压缩每次**只压一轮** |
| 压缩与提炼的配合 | **同一次调用同时产出**「1 条短期摘要 + N 条长期记忆」，两者都直接来自原始内容（兄弟，不是父子） |
| 降级与遗忘 | **名次驱动**：尾部降级 → 再叠加「降级次数 + 连续未召回」才遗忘 |
| 元记忆 | **加**：第 11 条之后只列关键词（一行一条，不给正文） |
| 归档 | 原始消息与摘要**一起**收口；当天摘要已先提升为长期记忆（修正，见 §4.5） |
| 夜间收口形态 | **树状**压缩（每轮分块各压一条），而非反复压「最旧 100 条」的链式做法 |

## 2. 一句话概括

> 上下文 = ① 永久记忆（全量）+ ② 长期记忆榜前 N 条正文 + 其后 M 条**关键词索引** + ③ 短期层（未合并的原始消息 + 更早的摘要块）+ ④ 当前消息 + ⑤ 作息提示。
>
> 长期记忆是一张**按「最后一次被想起」排序的榜**；短期记忆是一条**会自我压缩的时间线**。

预期效果：问「最近有人找我吗」时，答案就在 ② 的榜上和她自己的时间线里，不需要去翻。

## 3. 长期记忆：位置榜

### 3.1 上浮轴

新增列 `memories.promoted_at REAL NOT NULL DEFAULT 0`（最后一次上浮的时刻）：

- 新建 / 更新记忆（提炼、手工 `remember`）→ `promoted_at = now`
- 被召回（`mark_recalled`）→ `promoted_at = now`
- 榜序：`ORDER BY promoted_at DESC, id DESC`（`tier='long'`）

**为什么用时间戳而不是序号**：不用维护显式序号、不用整表重排，几千条也不会抖动。
现有的 `strength` 衰减与权重召回**退役**（不再衰减、不再参与排序）。

### 3.2 名次驱动的降级与遗忘

名次与总数由查询算出，等级仍是**纯函数推导、不入库**（沿用既有原则）：

```python
def curation_level(rank: int, total: int) -> int:
    ratio = rank / max(total, 1)
    if ratio <= 0.60: return LEVEL_FULL      # 完整
    if ratio <= 0.85: return LEVEL_BRIEF     # 精简
    return LEVEL_KEYWORDS                    # 关键词
```

- 降级：`curation_level` 落到精简/关键词档时，`curation_count += 1` 并重写正文（受 `curate_budget` 限制模型调用次数）。
- 遗忘（`_forget()`）三条同时满足才删，`tier='permanent'` 与 `forget_requested` 另走其道：

  1. 名次落在**后 5%**（`_FORGET_TAIL_RATIO`）
  2. `curation_count ≥ memory.forget_min_curations`
  3. `now - last_recalled_at ≥ memory.forget_stale_days`

- 晋升不变：`recall_count ≥ promote_min_recall` → `tier='permanent'`。

### 3.3 只插入前 N 条

| 区间 | 呈现 |
| --- | --- |
| 第 1 ~ `auto_top`（默认 10） | 完整正文（形态由 `curation_level` 决定） |
| 第 11 ~ `auto_index`（默认 40） | **只有一行关键词**，不给正文 |
| 第 41 之后 | 不进上下文，靠 `recall` 工具 |

索引行的写法是怕她「忘了自己忘了什么」——元记忆。一行 `- 老师的作息 / 白纸在准备考试 / …` 花费极小，却给了她主动回想的线索。

`recall` 工具的 docstring 要改成**明确邀请她「想一想」**（如「当你隐约觉得还有相关的旧事、需要确认细节时调用」），输出侧由她自然表现为「我想想」。
注意：**工具召回仍然按关键词相关性排序**，不按榜序——否则她会想起「榜上靠前但与当前话题无关」的事。榜序只决定自动插入。

### 3.4 永久记忆

`tier='permanent'` 全量、最早插入，不参与榜序、降级、遗忘。当前只有 5 条，若将来增长到几十条需要另设上限（本计划只标注风险，不实现）。

## 4. 短期记忆：分层压缩

### 4.1 条目与总数

**条目** = （`short_term_messages` 中 `condensed_at = 0 AND archived_at = 0 AND staged = 0` 的行）∪（`short_term_summaries` 中 `condensed_at = 0` 的摘要）。

**总数** = 两者条数之和。`总数 > memory.condense_threshold`（300）时触发一次压缩。

### 4.2 压缩：一次调用，两个产出

`extractor.py` 新增 `condense(rows) -> (summary, memories)`：

```json
{
  "summary": "一段 80~150 字的概括（谁、什么时候、大致发生了什么）",
  "memories": [{"content": "…", "keywords": ["…"], "source_quote": "…"}]
}
```

- `summary` → 写进 `short_term_summaries`（**短期层的远期背景**）
- `memories` → 写进 `memories`（`promoted_at = now`，直接上浮到榜首）
- 被覆盖的消息 `condensed_at = now`；被覆盖的旧摘要同样 `condensed_at = now`

**为什么必须同次产出**：原始行一旦 `condensed_at` 就退出上下文，如果这一步没同时产出长期记忆，这 100 条就永久消失且不报错——与「没提炼完就不许归档」是同一个坑。**模型失败时一律不标记 `condensed_at`**，原始行原样留着等下一轮。

### 4.3 二次合并只是阈值护栏

压缩的唯一职责是**减少上下文长度**，不是为了攒出多层摘要。白天的自动压缩是
「条目总数超 300 → 压掉最旧 100 条」，只要一整天都在阈值以下，它一次都不会触发。

旧摘要**当普通条目**参与选择（只占 1 条名额），对它不做任何特殊处理——它用
`covered_at` 定位，天然排在它所覆盖的那一段之后。所以「最旧的 100 条」在爆发日
会自然变成「1 条旧摘要 + 99 条较早的消息」→ 压成新高一层的摘要。这就是「二次合并」：
一个顺带的结果，不是必须发生的机制。

### 4.4 不再进上下文

- 时间线渲染时排除 `condensed_at > 0` 的消息与摘要。
- 摘要以 `<earlier_summary>` 包裹、`user` 角色插在它覆盖的那一段之后。
- 记忆页面与上下文**同源**：只显示「未合并的消息 + 摘要块」，已合并的原始行不列出（保留在库里供 P6 回查工具）。

### 4.5 归档与摘要的关系（推翻早期草案）

**摘要不豁免归档，也不跨天留存。**

- 深夜整理的最后一步 `clear_short_term()` 把短期层清空：原始消息标 `archived_at`，
  摘要标 `condensed_at`。**整理完短期层必须是空的**——否则「刚起床时短期记忆是空的」
  就不成立。
- 睡前 `collapse_short_term()` 先把整棵短期层**树状压成唯一一条「当天摘要」**，
  再把它作为**一条长期记忆**写进榜最前（`tags=["当天摘要"]`）：它是那一天唯一的
  遗留物，所以写得最详细（`_DAY_SUMMARY_CHARS = 400`）。
- 「细节慢慢变少」靠的是**名次**，不是再压一遍：当天摘要在榜首时是完整正文，
  日后被后来的记忆挤下去，才随名次进入「精简 / 关键词」档。
- 睡眠期间收到的消息不算短期记忆（`staged=1`），醒来放行后才入账、才参与当晚整理。
- `purge_expired()` 按保留期物理清理两类行：已归档的、已被压进摘要的。

## 6. 每日整理流程（替换现有九步）

```
1  维护        降级 → 遗忘 → 晋升 → 合并（maintainer.run，作用于原有那张榜）
2  短期收口    collapse_short_term()：树状压成唯一一条「当天摘要」
3  提升        当天摘要 → memories（tier=long，promoted_at=now，落在榜首）
4  清空        clear_short_term()：消息 archived_at、摘要 condensed_at
5  保留期清理  purge_expired()
```

**顺序是有意的**：收口放在维护之后，当天摘要最后写入，同刻并列时 id 最大，
于是**确定性地落在榜首**（榜序＝「她记得最牢的」，当天摘要必须是第一条）。

相比现状：**去掉**衰减、分会话淘汰、逐批提炼、重建历史；**替换**降级的判据。
硬保护保留：模型不可用 / 收口失败 / `daily_reset_enabled=False` 时**不清空**并告警。

**收口是「短期层 → 长期层」唯一的通道**，睡眠期暂存的消息在起床放行后，
和白天攒下的消息一起走这一步——不存在「漏掉某批」的路径。

## 11. 评审点（已定）

1. **摘要的注入角色**：定为 `user` + `<earlier_summary>` 标记。它不是「她说过的话」，
   而是一段被压扁的客观记录；混进 `assistant` 会让「我说过什么」失真。
2. **`covered_at` 的定位**：摘要按其覆盖区间的**末尾**入时间线（压扁的那段之后），
   读起来就是「先是模糊的一段，然后是最近发生的事」。
3. **索引条目数**：`auto_index` 定 30，`recall_token_budget` 1600；实机再微调。
4. **永久记忆上限**：仍为全量插入，当前体量（个位数）无风险；增长后再议。
