## 1. P6：`search_history`

### 1.1 定位

`peek_session` 看的是「现在」——走 `_LIVE_SQL`，只看得见还活着的条目。
一旦当天整理清空账本，昨天及更早的对话就再也看不见了。
`search_history` 补的就是这一段：**按关键词翻已经离开短期记忆的旧记录**。

两者边界：

| 工具 | 时间范围 | 检索方式 | 用途 |
| --- | --- | --- | --- |
| `peek_session` | **当下**（活着） | 取最近 N 条 | 「那边现在在聊什么」 |
| `search_history` | **全部**（含已清空 / 已压进摘要） | 关键词 + 会话 + 天数 | 「上周是不是提过某件事」 |

### 1.2 查什么

- **只查消息，不查摘要**。摘要没有 `chat_id`（它可能覆盖跨会话语段），按会话过滤时
  无法归属；而且她要看的是原文细节，摘要本身已经以长期记忆的形式在榜上。
- **包含活着的行**。工具语义是「翻聊天记录」，不是「翻归档」——模型不该先猜
  「这件事是不是今天说的」再选工具。`_LIVE_SQL` 是**上下文**的过滤器，不是检索的。
- **排除睡眠期暂存**（`staged = 1`）：那些消息在她醒来前不该存在，醒来后就 `staged = 0` 了。

### 1.3 签名

```python
@filter.llm_tool(name="search_history")
async def search_history(
    self,
    event: AstrMessageEvent,
    keyword: str = "",
    session: str = "",
    days: int = 7,
    limit: int = 20,
) -> str
```

| 参数 | 语义 |
| --- | --- |
| `keyword` | 关键词，留空 = 不限关键词（只按时间范围取最近若干条） |
| `session` | 会话；**留空 = 当前会话**（原计划确认的口径）。跨会话检索才显式填 |
| `days` | 往回查多少天，默认 7，夹在 `1 .. archive_retention_days`(90) |
| `limit` | 最多返回多少条，默认 20，夹在 `1 .. 50` |

docstring 写给模型看，要点明「**只在想确认旧事时用**，不要拿它代替回忆，
更不要把查到的内容当成本轮的话题」。

### 1.4 实现

新增 `ShortTermLedger.search_history(chat_id, keyword, since, limit)`：

```sql
SELECT * FROM short_term_messages
 WHERE staged = 0
   AND created_at >= ?                 -- since
   AND chat_id = ?                     -- 仅当指定了会话
   AND (content LIKE ? OR sender_name LIKE ? OR image_caption LIKE ?)
 ORDER BY created_at DESC, id DESC
 LIMIT ?
```

- 取回后在 Python 侧翻成时间正序，直接复用 `format_message_line()`——
  `[会话] 发言人 (多久前): 内容`，与时间线**同一套渲染**，她读起来不会割裂。
- 关键词用 `LIKE '%kw%'`：中文整词匹配够用；不做分词打分（这是「找具体一句」，
  不是语义检索，`recall` 才负责语义）。
- 图片描述（`image_caption`）一并匹配：她「看见过」图，就该能从描述里找到它。
- 结果前加一行元信息：`共 N 条（近 D 天，关键词「X」）`，让她知道自己看到的是
  筛选后的片段，而不是全部。

### 1.5 明确不做

- 不做自动注入、不参与 `recall()` 打分：它是**主动**回查，和记忆注入是两条路。
- 不复用 AstrBot 的 `get_group_message_history`（只支持群聊、默认关闭、滚动窗口）。

## 2. P7：`delay_sleep`

### 2.1 签名与语义

```python
@filter.llm_tool(name="delay_sleep")
async def delay_sleep(self, event: AstrMessageEvent, hours: float) -> str
```

| 项 | 规则 |
| --- | --- |
| 取值范围 | `0.5 ~ 6` 小时；超出直接拒绝并说明范围 |
| 生效方式 | `postponed_hours += hours`，入睡与起床一起顺延 |
| 上限 | 顺延后 `wake_at` 不得超过 `wake_latest`；超了拒绝，并告知「还能推迟 X 小时」 |
| 时机 | **只在清醒（`phase == AWAKE`）时允许**。已经躺下（浅睡/深睡）再推迟等于「起床」，会打乱整理节拍，直接拒绝并说明 |
| 持久化 | `sleep_state.save(postponed_hours=..., sleep_at=..., wake_at=...)`，重启可恢复 |
| 内存 | 立刻 `_refresh_sleep_window()`，本 tick 之后的状态推导就用新窗口 |
| 周期 | **只对当次作息生效，次日回到基础时间表** |

docstring 要点：这是「今晚想再待一会儿」的表达，不是改作息表；一次只推一点点，
不要因为它能做就随便推。

### 2.2 为什么不让它在睡眠中生效

`sleep_at` 往后推会让 `phase_at()` 立刻从 `LIGHT/DEEP` 回到 `AWAKE`——技术上
「推迟」等于「把已经开始的睡眠撤回去」。这既不符合语义，又会把当晚的整理节拍
（`DEEP` + 满 24h 才收口）整段挤掉。所以睡眠中一律拒绝。

### 2.3 顺带修掉的 bug：推迟会跨天累积

`_sleep_tick()` 跨天时做的是：

```python
postponed = float(state.get("postponed_hours") or 0.0)
window = plan_window(now, cfg, postponed)
if state["plan_date"] != window.plan_date:
    self.sleep_state.reset_round(window, postponed)   # ← 把旧值原样写回
```

于是「推迟 3 小时」会一直生效下去，与 §2.1 的「只对当次」直接矛盾。
修法：跨天分支里把 `postponed` 归零、并用 0 重算窗口后再 `reset_round`。
`previous_wake` 仍需在重算**之前**取（它来自旧 state）。

> 这个 bug 在 `delay_sleep` 落地之前没有可见后果（没人写 `postponed_hours`），
> 所以一并放在 P7 修。

## 3. P7：记忆页面展示作息

### 3.1 接口

`overview` 增加 `sleep` 段（只读）：

```json
{
  "phase": "deep",
  "sleep_at": 1790000000.0,
  "wake_at": 1790026800.0,
  "postponed_hours": 1.0,
  "last_curation_at": 1789990000.0,
  "next_curation_at": 1790076400.0
}
```

- 数据来源：`sleep_state.load()` + `plan_window()`（现算，不存中间态）。
- `sleep.enabled = false` 时整段返回 `null`——作息关掉后这些时刻没有意义。
- 由 `main` 暴露一个只读快照方法，`web_api` 只负责序列化（页面不直接读库）。

### 3.2 页面

记忆页面顶部统计区下方加一条**作息条**：

```
深睡中 · 23:30 入睡 / 07:00 起床（本轮推迟 1 小时） · 上次整理 6 小时前
```

- 阶段中文化：`awake` 清醒 / `light` 浅睡 / `deep` 深睡。
- 推迟为 0 时不显示括号那段。
- 上次整理从未发生（`last_curation_at = 0`）时显示「尚未整理」。

等级与召回次数已在「长期记忆」分页展示（名次、档位标签、`召回 N 次`），本轮不动。

## 5. 验证计划（容器内）

1. **回查覆盖三类行**：活着 / 已压缩（`condensed_at > 0`）/ 已清空（`archived_at > 0`），
   三类都能被 `search_history` 搜到；`staged = 1` 的死活搜不到。
2. **过滤正确**：默认只查当前会话；显式 `session` 能跨会话；`keyword` 命中 content /
   `sender_name` / `image_caption` 三列；`days` 与 `limit` 生效且被夹紧。
3. **摘要不进结果**：`short_term_summaries` 里的内容不出现在返回里。
4. **推迟生效**：`AWAKE` 下 `delay_sleep(2)` → `plan_window().sleep_at/wake_at` 各顺延 2h。
5. **上限拒绝**：推迟到 `wake_latest` 附近再推 → 返回错误且含「还能推迟 X 小时」。
6. **时机拒绝**：`LIGHT` / `DEEP` 下调用 → 拒绝，`postponed_hours` 不变。
7. **只对当次生效**：模拟跨天 tick → `postponed_hours` 归零、窗口回到基础时间表。
8. **展示**：`overview.sleep` 字段齐全；作息关闭时为 `null`。
9. `compileall` + `import astrbot_plugin_shittim.main` + schema/i18n JSON 校验。

## 7. 已确认（原待确认项）

1. **`search_history` 包含「活着的」当天消息** —— 是。工具语义是「翻聊天记录」，
   不是「只翻归档」；否则模型得先猜这件事是不是今天说的，再决定用哪个工具。
2. **`delay_sleep` 在浅睡/深睡时拒绝** —— 是。推迟等于把已开始的睡眠撤回，
   还会挤掉当晚的整理窗口。
3. **默认只查当前会话** —— 是。跨会话必须显式填 `session`，否则一次搜索会把
   所有会话的旧记录都翻出来。

## 8. 追加：人格预设对话的保留

### 8.1 检查结论

| 位置 | 内容 | 是否被本插件影响 |
| --- | --- | --- |
| `req.system_prompt` | `# Persona Instructions` 人格说明 | **不受影响**——本插件从不写这一栏 |
| `req.contexts[:0]` | 人格的 `begin_dialogs`（预设对话 / 说话示例） | **会被整体替换抹掉** |

AstrBot 的执行顺序是：`build_main_agent` → `_ensure_persona_and_skills()`（把
`begin_dialogs` 插到 `contexts` 最前）→ `call_event_hook(OnLLMRequestEvent)`（本插件
在这里整体替换 `contexts`）。所以人格说明安全，预设对话不安全。

实测当前四个人格（爱丽丝 / 爱丽丝简化版 / 爱丽丝人格削弱版 / default）的
`begin_dialogs` 全为 `[]`，**此前没有实际损失**；但主人一旦给某个人格配上预设对话，
它就会被静默丢掉。

### 8.2 修法

`main._persona_dialogs(contexts)`：取 `contexts` **头部连续**的 `_no_save` 段
（AstrBot 插入的每一条都带这个标记），在替换时 `req.contexts = persona + rendered`。

不用「长度差」或「role 组合」去猜：`_no_save` 是 AstrBot 自己打的标记，最可靠；
且它别处追加的系统条目（如文件解析结果）不带这个标记，不会被误认。
