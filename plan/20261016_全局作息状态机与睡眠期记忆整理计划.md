## 1. 背景与目标

什亭之枢目前没有作息概念：她 7×24 在线，任何消息都会进决断层，记忆维护只靠
`_schedule_maintenance_if_due()` 的 24 小时兜底（`_MAINTENANCE_FALLBACK_SECONDS`）。

本计划引入**跨会话共享的全局作息状态机**，并让「睡眠」成为记忆整理的主要时机：

- 有明确的人作息边界（入睡 / 起床），睡眠期间不消耗任何模型调用
- 浅睡可被叫醒，深睡不可
- 深睡期用模型做短期账本压缩与长期记忆精简
- 长期记忆的遗忘改为**确定性判据**，消除不可复现行为

### 目标（本期做）

1. 状态机：清醒 / 浅睡 / 深睡，跨会话共享、跨重启持久化
2. 作息时间表 + 模型可推迟入睡（顺延起床，有上限）
3. 睡眠期间：**记账但不进模型**，命令（`/` 指令）例外、仍照常放行
4. 叫醒机制与叫醒提示注入
5. 起床机制、起床时间提示、起床后回复睡眠期消息
6. 深睡期定时记忆整理：**提炼覆盖扩展** + **记忆曲线逐级精简**
7. 长期记忆遗忘：**确定性阶梯**（曲线等级 + 整理次数 + 未召回天数）
8. **每日重置**：整理后清空清醒期账本，并把各会话原生历史收缩重建
9. **四段式注入顺序**：永久记忆 → 长期记忆 → 短期记忆 → 起床提示

### 非目标（本期不做）

| 项 | 原因 |
| --- | --- |
| 永久记忆内容改写 / 打补丁 | 会破坏「永久记忆 = 稳定锚点」的唯一价值，且存在提示注入篡改风险 |
| 睡前告别文案 | 路线图第 3 条，独立特性，另开计划 |
| 作息可视化面板 | 路线图第 4 条 |
| 记忆手工编辑 / 删除 | 路线图第 5 条 |
| 困意值 | 已确认本期不引入，见 §4.3 |
| 独立归档层（永久保留原始对话 + 回查工具） | 已确认改用「提高提炼覆盖 + 内置历史工具」，见 §9.4 / §9.7 |
| 新增第三个记忆模型入口 | 会与 `extract()` / `merge()` 互相覆盖，见 §9 |

## 2. 已确认的决策

| 决策点 | 结论 |
| --- | --- |
| 睡眠期间的消息 | **记账但不进模型**：写入短期账本（`source='sleep'`、`staged=1`）并参与叫醒计数，但不触发决断层与主脑 |
| 起床后 | 睡眠期消息**直接进入短期记忆、参与后续提炼**（`staged` 置 0，标记保留） |
| 叫醒阈值 | 同一会话 **5 分钟内 3 次** @ / 私聊 |
| 叫醒后的焦点范围 | **只**让叫醒她的那个会话获得焦点，不批量恢复 |
| 深睡整理轮次 | **每晚一次**（距上次 ≥ 24h 且处于 `DEEP`），另有 48h 兜底；不是每小时一次 |
| 整理用的模型 | **直接用记忆提炼模型**，不单独配"上下文清理模型" |
| 记忆曲线的降级 | **全部**长期记忆整体降、每天一级；召回 `+3`；`curation_score` 下限 `-1` |
| 长期记忆遗忘判据 | **确定性阶梯**：`score < 0` + 降级次数达标 + 连续 N 天未召回（不用概率） |
| 永久记忆补丁 | 本期不做 |
| 「上下文每天干净」的实现 | **改写 AstrBot 原生历史**（`conversation_manager.update_conversation`），不接管 `req.contexts` |
| 重建范围 | **全部已知会话**都收缩为"近空白 + 起床提示" |
| 「清空」的语义 | **移入归档**（`archived_at`）而非物理删除；常规查询与上下文都排除它 |
| 模糊记忆怎么找回 | **自建 `search_history`**，覆盖群聊与私聊，不依赖 AstrBot 的 `group_message_history_enable` 开关 |
| 被拦消息（gated）跨天 | **取消固化**，只靠归档 + `search_history` 检索（**已确认**） |
| 「第二天失忆」的取舍 | **提高提炼覆盖**（纳入当天重点事件），不建独立归档层 |
| 困意值 | 本期不引入 |
| 推进方式 | 先出本计划，用户确认后再实现 |

## 3. 状态与阶段

### 3.1 三个状态

| 状态 | 含义 | 进模型 | 可被叫醒 |
| --- | --- | --- | --- |
| `AWAKE` | 清醒 | 是 | — |
| `LIGHT` | 浅睡 | 否 | 是 |
| `DEEP` | 深睡 | 否 | 否 |

### 3.2 阶段由时间轴推导（纯函数）

状态不是靠事件累积出来的，而是 `now` 的**纯函数**，只有「被叫醒后的清醒宽限」
是一个覆盖层。这样重启后不需要恢复任何中间态，算一次就知道该在哪。

```
输入：sleep_at（入睡时刻）、wake_at（起床时刻）
wake_notice_lead = 2h（起床前转浅睡）
light_min_duration = 2h（浅睡满这么久转深睡）

phase(now):
    若 now ∉ [sleep_at, wake_at)         → AWAKE      # 不在睡眠窗口
    若 now >= wake_at - wake_notice_lead → LIGHT      # 起床前 2h 强制浅睡
    若 now - sleep_at >= light_min_duration → DEEP
    否则                                  → LIGHT

覆盖层：
    grace_until > now → AWAKE（清醒宽限，正常处理消息）
```

**为什么这样建模**：「浅睡 2h 后进入深睡」与「起床前 2h 变浅睡」在时间上是重叠的
两条规则，如果各自维护独立计时器，会出现「深睡中却显示可被叫醒」的矛盾。做成时间轴
函数后，两条规则天然按先后顺序生效，不会打架。

### 3.3 状态转换图

```
        ┌─────────────────────── 起床时刻 wake_at ───────────────────────┐
        │                                                                │
        ▼                                                                │
   ┌────────┐  入睡时刻 sleep_at   ┌────────┐  浅睡满 2h   ┌──────┐      │
   │ AWAKE  │ ───────────────────▶ │ LIGHT  │ ───────────▶ │ DEEP │      │
   └────────┘                      └────────┘              └──────┘      │
        ▲                               ▲                      │         │
        │                               │                      │         │
        │      叫醒成功（@ / 私聊 达标）  │  10 分钟无 @/私聊     │         │
        └───────────────────────────────┴──────────────────────┘         │
        │                                      ▲                         │
        │                                      │ 起床前 2h 强制转浅睡      │
        └──────────────────────────────────────┴─────────────────────────┘
```

## 4. 作息时间表

### 4.1 基础时间表（可配置）

配置在新增的 `schedule` 组（见 §12）。默认值：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `sleep_at` | `23:30` | 基础入睡时刻（本地时间） |
| `wake_at` | `07:00` | 基础起床时刻 |
| `wake_latest` | `12:00` | 起床时间上限，推迟不得越过 |
| `wake_notice_lead_minutes` | `120` | 起床前多久转浅睡 |
| `light_until_deep_minutes` | `120` | 浅睡多久转深睡 |

`wake_at` 与 `sleep_at` 的差值即睡眠时长，不做单独配置（避免两处真值）。

关于「模型应该有个作息时间表，决定起床和入睡时间」的口径：本计划把时间表定义为
**基准**（由配置给出），模型的自主权体现为在其之上的**推迟**（§4.2）。这样作息是
可预测、可排障的；若让模型每次自行重排整个时间表，就变成每天都不一样、无法解释的
行为。

> 待确认：以上口径是否符合你的设想。若你希望模型能整体重排时间表（而不只是推迟
> 入睡），需要额外增加一个设置时间的工具，并明确"它多久可以改一次"。

### 4.2 推迟入睡

模型可通过新增的 LLM 工具 `delay_sleep(hours)` 自主推迟入睡：

- 每推迟 1 小时，起床顺延 1 小时：`wake_at = min(基础 wake_at + 已推迟小时数, wake_latest)`
- `sleep_at = wake_at - 睡眠时长`
- 到达 `wake_latest` 上限后不再允许推迟（工具返回错误说明，而不是静默无效果）
- 推迟只对**当次**作息生效，次日回到基础时间表

> 需要确认：`wake_latest = 12:00` 是「起床上限」还是「入睡上限」。本计划按**起床上限**设计。

### 4.3 困意值：本期不引入

**已确认：不加入困意值。**

理由（记录备查）：本设计已经有三套驱动——基础时间表、模型推迟入睡、起床前 2h 转
浅睡。再引入一个独立真值，就会出现「该听时间表还是听困意」的双真值问题；一旦某天
没按时睡，无法从日志判断是哪个变量导致的。而"睡前渐进困倦"这层表现力，靠
`sleep_at` 前后的时间提示已经足够表达。

若将来确实想要「渐进困倦」，正确的做法是把它定义成**只读纯函数**
（`sleepiness(now) = f(now, sleep_at)`），作为描述而非状态机开关——届时再评估。

### 4.4 入睡机制

到达 `sleep_at` 时，由后台 tick 触发一次**入睡收口**：

1. **撤销所有焦点**：复用 [`FocusManager.rest()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/focus/manager.py#L84-L89)，
   一次性收回所有会话的主动发言资格（她"去睡了"，不再主动关注任何地方）
2. **清零叫醒信号计数**：避免睡前残留的 @ 在入睡后立刻把她叫醒
3. **写入 `sleep_state`**：`sleep_at`、`wake_at`、`plan_date`、`postponed_hours`
4. 状态由时间轴推导为 `LIGHT`（`now` 刚进入窗口且未满 2h）
5. **不做睡前告别**：路线图第 3 条的独立特性，本期非目标（见 §1）

入睡是**静默**的：她不会主动广播"我睡了"。这是刻意的——主动告别会把"她在睡觉"
这件事变成所有人都知道的公开信息，而她只该表现为"没回应"。

## 5. 叫醒机制

### 5.1 计数规则

- 只有 **@ 她** 或 **私聊消息** 计入叫醒信号（群聊普通消息不计）
- 计数按**会话**独立，不跨会话合并（避免多个群各说一句就"凑齐"）
- 滑动窗口内累计达到阈值即叫醒：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `wake_signal_window_minutes` | `5` | 信号有效窗口 |
| `wake_signal_threshold` | `3` | 窗口内达到几条即叫醒 |

**已确认：同一会话、5 分钟窗口内累计 3 次 @ / 私聊即叫醒。**

### 5.2 叫醒结果

叫醒成功（仅在 `LIGHT`，`DEEP` 一律不响应）：

1. 置 `grace_until = now + wake_grace_minutes`（默认 10 分钟）→ 状态进入 `AWAKE`
2. **聚焦系统启动**：对叫醒她的那个会话调 `focus.touch()`，让她重新有资格在那边
   主动说话（否则 [`_check_say_gate()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/main.py#L1183-L1214)
   会因无焦点把她拦下）。其它会话不批量恢复——下一次有人说话时自然获得焦点
3. 记录 `awakened_at`，供「叫醒提示」判断是否已注入过
4. 该条消息**放行**主脑（这不是"睡眠期消息"，是被叫醒的那一条）

宽限期内每来一次 @ / 私聊就刷新 `grace_until`；超过 10 分钟无信号 → 覆盖层自然失效，
状态落回 `phase(now)`（通常是 `LIGHT`）。

**已确认：只让叫醒她的那个会话获得焦点**，不批量恢复入睡前被 `rest()` 撤销的全部焦点。
即她刚被叫醒时只看得到眼前这个会话，其它会话等下一次有人说话时自然获得焦点。

## 6. 睡眠期间的拦放（事件链）

### 6.1 执行顺序

```
记账 100  record_incoming_message     ← 睡眠期照常记账（source='sleep', staged=1）
睡眠门 95  sleep_gate                 ← 新增：判定并拦截，必须先于决断层规则层
决断 90    gate_official_llm
注入 -10   inject_memory_context
```

**为什么必须新增 95 这个 handler，而不是塞进 `gate_official_llm`**：决断层的
[`rule_decide()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/gate/engine.py#L110-L133)
里私聊是 `always_reply_private=True` 直接放行。睡眠判定若晚于它，私聊会直接穿透给主脑。
放在 90 之前是唯一可靠的位置。

同时睡眠门的判定必须是**零 token 的同步规则**（只看时间轴 + 计数），不能调用模型——
否则"睡眠时不消耗任何模型调用"这条前提就破了。

### 6.2 前置规则与三态处理

**第一优先级：上游命令一律放行。**

需求原文是「忽略一切**非命令**消息」，所以命令必须能穿透睡眠门：

| 判定顺序 | 处理 |
| --- | --- |
| 1. 上游指令（`/命令`、skill） | 直接 return，交回原生链路 |
| 2. 其余消息 | 按下面的三态处理 |

命令放行直接复用决断层已有的判据
[`is_upstream_command_event(event)`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/gate/engine.py#L120-L122)，
不另写一套识别逻辑。

若不放行命令，睡眠期间 `/` 指令会整段失效——连"提前起床""看看现在几点"这类本该
随时可用的运维指令都做不到。

注意：命令放行**不**解除睡眠状态、也**不**开启清醒宽限。它只是"让路"，与她在不在睡
无关。

三态处理：

| 状态 | 命令 | 非命令消息 |
| --- | --- | --- |
| `AWAKE` | 放行 | 放行，交回原有链路 |
| `LIGHT` | 放行 | 累计叫醒信号；达标 → 放行 + 开宽限；未达标 → `stop_event()` 拦下 |
| `DEEP` | 放行 | 一律 `stop_event()` 拦下，不计数、不响应 |

### 6.3 睡眠期消息的账本来源标记

现状 `gated=1` 的消息会被 [`merge_missing_into_contexts()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/history.py#L227-L316)
**全量**插回 `req.contexts`，没有 token 预算。睡眠 8 小时可能积压几百条，直接合并会
撑爆窗口。

因此新增一个 `source` 取值，并配一个 `staged` 标记（两者职责见 §9.2）：

| `source` | 含义 | 是否参与合并回 contexts |
| --- | --- | --- |
| `live` | 正常实时消息 | 是（gated=1 时） |
| `backfill` | 官方历史回填 | 否 |
| `sleep` | **睡眠期间收到的消息** | **否**，改由起床提示块按 token 预算呈现 |

`short_term.add()` 增加 `source` 传参；`staged` 是新增列（见 §13.3），睡眠期记账置 `1`。

**深睡期的记账口径**：需求写的是深睡「不监听任何消息」。本计划把它解释为
**不响应、不计数、不判定**，但**仍然记账**——理由是你在「睡眠期间消息怎么处理」
上已确认「记账但不进模型」，深睡只是睡眠的一种，口径保持一致她醒来才不会失忆。

> 待确认：若"不监听"你的本意是**连账都不记**（睡眠期间的对话对她彻底不存在），
> 那深睡期需要在 `record_incoming_message` 里也加一层判断——这会让"睡前"和"深睡期"
> 的记忆完整性不一致，请明确取哪一种。

### 6.4 睡眠期与焦点系统（实现陷阱）

记账在优先级 100，而 [`record_incoming_message`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/main.py#L255-L257)
是**无条件**调 `focus.touch(chat_id)` 的。如果睡眠期间照常 touch，就等于把「她睡了」
这件事静默撤销：每个说话的会话都重新拿到主动发言资格，与 §4.4 的 `rest()` 直接相抵。

处理方式：

- 睡眠期间（`LIGHT` / `DEEP`）**不刷新焦点**——在 `touch()` 之前加一眼状态判断
- 改为在**起床时**统一 `touch()` 睡眠期间有消息的会话（§7.3），让她有资格回去回应
- 叫醒时 `touch()` 叫醒她的那个会话（§5.2）

这样「她在谁那里有发言资格」始终由「醒着时的活跃会话」决定，语义干净，也不会
出现"她睡了八小时，醒来却同时关注着十几个群"的情况。

## 7. 起床机制

### 7.1 触发

- 通过后台定时器在 `wake_at` 到点触发（见 §14）
- 计算并持久化 `wake_notice_pending = 1`（有待注入的起床提示）
- 状态不再是覆盖层，直接由时间轴推导为 `AWAKE`

### 7.2 起床提示注入

在起床后**第一次**进入主脑请求时注入，注入的是：

1. 起床时间（绝对时间，便于她知道自己睡了多久）
2. 睡眠期间是否有消息，以及最近若干条的摘要（受 token 预算约束）

注入位置：`req.contexts = prefix + req.contexts + [起床提示]`，即紧邻 `req.prompt`
的**最新处**。

**为什么放最新处而不是像其它背景块一样放最前**：这是一条**时效性事件通知**
（「你刚醒」），不是长期背景。放在历史之前会被当成很久以前的信息。

**为什么必须持久化 `wake_notice_pending` 标记**：注入块每次请求都会重建，若不记录
「是否已注入过」，这条提示会在起床后的**每一轮**对话里重复出现。注入后立即清标记。

### 7.3 起床后回复睡眠期消息

#### AstrBot 提供的主动通路（已核实源码）

| 通路 | 能力 | 是否经过主脑 |
| --- | --- | --- |
| `context.send_message(session, chain)` | 发固定消息链 | 否，不调模型 |
| `context.llm_generate(...)` / `provider.text_chat(...)` | 插件自己调模型拿文本，再自行发送 | 否，**没有人格、没有工具、没有 `on_llm_request` 注入** |
| `context.tool_loop_agent(event=...)` | 自建带工具的 agent 循环 | 接近主脑，但**必须传一个 event** |
| `CronJobManager.add_active_job(...)`（`job_type="active_agent"`） | 官方定时唤醒主脑：构造 `CronMessageEvent`（`AstrMessageEvent` 子类）→ `build_main_agent()` → `step_until_done()`，并给 agent 挂上内置 `SendMessageToUserTool` 让它自己发出去 | **是** |

注意：`/AstrBot/data/plugins/` 下那些"订阅后推通知"的插件，绝大多数走的是前两条——
要么发模板文本，要么自己调模型再发，**都不经过主脑**。

所以「插件完全无法主动发起」的说法不成立，第四条通路确实是官方的主动唤醒机制。

#### 关键坑：主动通路不触发 `on_llm_request`

`on_llm_request` 只在 pipeline 的两个阶段被触发（AstrBot 源码
`astrbot/core/pipeline/process_stage/method/agent_sub_stages/third_party.py:333`
与 `.../internal.py:307`）。而 `CronJobManager._woke_main_agent()` 是**直接构造
`ProviderRequest` 并调 `build_main_agent()`**，绕过 pipeline；主脑运行时的
`MainAgentHooks` 只触发 AgentBegin / LLMResponse / AgentDone / Tool 四类事件，
**不含 `OnLLMRequest`**。

若起床批处理直接走 `active_agent`，会踩到三个已知设计约束：

| 后果 | 说明 |
| --- | --- |
| 记忆注入失效 | `inject_memory_context`（长期记忆 + 别处经历 + gated 合并）不会被调用，她起床后是"失忆"状态开口 |
| 内置发送工具复活 | `hide_builtin_send_tool` 同样不生效，`send_message_to_user` 又可用，绕过 `say` 的会话解析与焦点校验 |
| 她的话不入账 | `after_message_sent` 不触发，起床后说的话不会被记入短期账本 |

#### 本计划的选择

**采用方案 A（不主动唤醒）**，理由是与现有架构约束一致、改动最小：

1. 起床提示里明确告诉她「睡眠期间这些会话找过你」
2. 她已有 `list_sessions` / `peek_session` / `say` 三个工具，可自主决定去哪个会话回应
3. 这些睡眠期会话在起床时统一 `focus.touch()`，保证她**有资格**主动 `say` 过去
   （否则 [`_check_say_gate()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/main.py#L1183-L1214)
   会因无焦点而拦下）

即：起床后回复 = **给她信息 + 给她资格**，由她在下一次请求里自主完成。这与现有
「行动链路」设计一致，不引入新的发送通路。

> 备选方案 B（记录备查，本期不采用）：用 `CronJobManager.add_active_job()` 主动唤醒。
> 若将来要做，**必须手动补齐**上面三项：把注入块塞进 `req.contexts`、手动摘除
> `send_message_to_user`、跑完后手动把她的发言记入账本。否则会静默绕过本插件三条
> 核心防线——这是"看起来能用、实际在漏"的典型陷阱。

### 7.4 起床后的注入顺序（四段式）

需求指定的读取顺序：

```
① 永久记忆 → ② 长期记忆 → ③ 短期记忆 → ④ 起床提示 →（原生历史）→ 当前消息
```

与改动前的差异只有一处：原先 `build_block()` 把 `tier='long'` 与
`tier='permanent'` 混成一个 `<memory_reference>` 块，需要**按 tier 拆成两块**。
`memories` 表已有 `tier` 字段，改动很小。

> 已实现为 [`build_blocks()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/injector.py#L110-L142)：
> 按 ① 永久 → ② 长期 出块，token 预算**两块共用**（永久先占，剩下的才轮到长期）。

| 段 | 内容 | 来源 | 现状 |
| --- | --- | --- | --- |
| ① 永久记忆 | `tier='permanent'` | `store.recall()` | 需从混合块里拆出 |
| ② 长期记忆 | `tier='long'` | 同上 | 同上 |
| ③ 短期记忆 | 当天账本（含起床时搬入的睡眠期消息） | [`build_recent_block()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/ledger.py#L290-L336) | 已存在，位置已符合 |
| ④ 起床提示 | 时效性事件通知 | §7.2 | 新增，放最新处 |

注意 ④ 的位置与前两段不同：①②③ 都在**原生历史之前**（长期背景），④ 紧邻
`req.prompt`（时效事件），与 §7.2 的说明一致。

## 9. 深睡期记忆整理

### 9.1 触发：每晚一次

**结论：一晚整理一次，不是每小时一次。**

| 项 | 取值 |
| --- | --- |
| 主触发 | 当前处于 `DEEP` **且** `last_curation_at < sleep_at`（本轮深睡窗口里还没整理过） |
| 兜底触发 | 距上次 ≥ `curation_force_after_hours`（默认 48）且**不在** `DEEP` → 只做整理类步骤，**不清空、不重建**，并告警 |
| 检查节拍 | 后台 tick 每 60 秒看一眼，满足条件才真正开工 |

**为什么不是每小时**（对照 §9.3 十步逐项看）：

| 步骤 | 多跑的效果 |
| --- | --- |
| 衰减 | **幂等**——按实际经过时间算，跑 8 次与跑 1 次总衰减量相同 |
| 降级 | 有 `demote_interval_hours` 护栏，跑 8 次也只降一级 |
| 晋升 / 遗忘 / 淘汰 | 幂等，条件满足即生效 |
| 合并 | 候选受 `merge_min_age_days` / `merge_max_strength` 限制，几轮后自然无候选 |
| 归档 | 第一次做完后即为空操作 |
| 重建历史 | 反复重写同一份"近空白"，无意义 |

即：多跑**不带来额外效果**，只增加全表扫描、写库与模型调用。

**为什么用「距上次」而不是「进入 DEEP 那一刻」**：前者天然防重启重跑（重启后时间差
没到就不会重跑），也防一晚多跑；后者每次进程重启都会把整晚的整理重做一遍。

**为什么必须有兜底**：当睡眠时长短于 `light_until_deep_minutes + wake_notice_lead`
时，`DEEP` 阶段会被完全挤掉（例如睡 3 小时：浅睡 2h 之后立刻进入"起床前 2h 转浅睡"），
整理将永不发生。兜底路径刻意**不做清空与重建**——清醒状态下清账本等于当场失忆。

> 关于"每天清空"的**时点**：清空发生在**深睡期的这一次整理**，而不是某个固定的
> "每日零点任务"。因为睡眠期消息是 `staged = 1` 且不参与清空，所以不存在
> "作息被推迟到凌晨、零点任务却提前清了"这类时序错乱。

### 9.2 两级存储：清醒期账本 / 睡眠期暂存

"整理完短期为空"与"睡眠期消息要留到起床"不能共用一个表，必须拆成两套生命周期：

| 层 | 内容 | 整理时 | 起床时 |
| --- | --- | --- | --- |
| **清醒期账本** | 白天累积的消息（`staged = 0`） | 提炼后**清空** | — |
| **睡眠期暂存** | 睡眠期间收到的消息（`staged = 1`） | **不参与整理、不清空** | `staged` 置 `0`，纳入正常流程 |

实现用**两个字段各管一件事**，不新建表：

| 字段 | 职责 | 取值 |
| --- | --- | --- |
| `source` | **来源事实**，用于在上下文里标明"昨晚睡觉时收到的" | 新增取值 `sleep`；起床后**保持不变** |
| `staged` | **是否仍在睡眠暂存区**，用于整理排除 | 睡眠期记账置 `1`；起床置 `0`；默认 `0` |

**为什么不让 `source` 一肩挑**：来源是**永久事实**（"这条是睡觉时收到的"永远成立），
而"是否参与整理"只在睡眠期间成立。若只用一个字段、起床时把它改回 `live`，那"睡觉时
收到"这个标记就被抹掉了——而需求明确要保留这个标记。

整理时 `DELETE ... WHERE staged = 0`；起床时 `UPDATE ... SET staged = 0 WHERE staged = 1`。
[`format_message_line()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/ledger.py#L41-L74)
对 `source='sleep'` 追加「（睡觉时收到）」标记。

**"不参与整理"包括提炼**：§9.3 第 1 步只取 `staged = 0` 的行，睡眠期消息不受影响。

> 已实现：`pending()` / `pending_count()` 均加 `staged = 0`；`format_message_line()`
> 对 `source='sleep'` 补「（睡觉时收到）」（只改行格式，不动 `content`）。
> 另：判断"是否睡眠期"时排除了宽限期——刚被叫醒那 10 分钟她是醒着的，那段消息算实时消息。

**已确认：起床后直接进入短期记忆，参与后续提炼。** 起床把 `staged` 置 0 之后，
它们就走常规的 `_schedule_extraction_if_needed()`（回复后检查、攒够一批才提炼），
会被提炼成长期记忆，`source='sleep'` 的标记照留。否则会出现「昨晚有人说『明天下午
三点开会』，她起床看到并回复了，但这条信息永远不会进长期记忆」的洞。

**睡眠期暂存仍受上限保护**：它不被整理清空，但必须有兜底，否则长期不受理（如插件被
停用、作息表异常）会无限增长。沿用现有 `short_term_max_messages`（按会话分组淘汰）
对 `source='sleep'` 同样生效——原 `prune()` 保留在流程里，只是不再承担"清空"职责。

### 9.3 整理流程（顺序固定）

```
1. 提炼    _extract_all()                循环提炼至 pending 为空（只处理 staged=0）
2. 衰减    maintainer._decay()
3. 降级    maintainer._demote()          每天最多降一级（§9.6）
4. 晋升    maintainer._promote()
5. 合并    maintainer._merge()
6. 遗忘    maintainer._forget()          确定性阶梯判据（§10）
7. 淘汰    short_term.prune()            睡眠期暂存按上限兜底（§9.2）
8. 归档    short_term.archive_live()     清醒期账本移入归档（archived_at = now，§9.7）
9. 重建    _rebuild_native_history()     改写原生历史（§9.5）
```

**第 1 步必须循环，不能只跑一次**：现有
[`_run_extraction()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/main.py#L970-L1016)
一次只取 `extract_batch_size`（默认 40）条。如果睡前积压了 400 条未提炼消息，
单次提炼只处理 40 条，**剩下的会被第 8 步归档掉——虽然还能 `search_history` 查到，
但永远进不了长期记忆**。

所以本步骤改为**循环提炼直到 `pending_count() == 0`**，并设安全上限
（`extract_max_rounds_per_curation`，默认 20 轮）。触顶仍有 pending 时：
**跳过第 8、9 步**并告警——宁可这一次不归档，也不能让一批消息漏出长期记忆。

**只处理 `staged = 0`**：睡眠期消息留给起床后走常规提炼路径。
凌晨那几条消息单独提炼质量很差（缺语境、批次碎），而现有
`extract_batch_size = 40` 的设计意图正是"攒够一批、语境完整再提炼"。

**硬保护**：`extractor.available == False`（未配置 `extract_provider_id`）时
**禁止执行第 8、9 步**，只跳过本次整理并告警。否则会每天静默把一整天的对话移出
常规路径（含巡检、注入、提炼），且不报任何错。

沿用**既有的两条模型管线**（`extract()` / `merge()`），**直接用记忆提炼模型**，
不新增第三个 prompt 入口、也不单独配"上下文清理模型"——三个模型各改同一批数据、
规则不同、互相覆盖，无法回溯是哪一次改的。

### 9.4 提高提炼覆盖（针对"第二天失忆"）

现有 [`_EXTRACT_PROMPT`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/extractor.py#L29-L69)
的【不值得记住】明确排除"一次性闲聊"，这正是"第二天问昨天那件事就失忆"的根因。
按需求把提炼目标从"稳定事实"扩展到**"当天的重点事件"**：

- 【值得记住】新增一类：**当天发生的事件及其结论**（谁做了什么、讨论出了什么结果）
- 仍保留【不值得记住】里的"纯寒暄 / 复读 / 表情"，避免退化成流水账
- 相应提高 `extract_max_items`（默认 5 → 建议 12）与放宽正文长度上限

> 权衡：覆盖提高必然让长期记忆条目变多、注入预算吃紧。**缓解手段是 §9.6 的记忆
> 曲线**——新增条目会随整理次数被逐级压缩，最终只剩关键词或被遗忘。
> 即"广度靠提炼、长度靠精简"，两条必须一起上，单上一条都会失衡。

> 已实现：`_EVENTS_CLAUSE` 由 `memory.extract_include_events`（默认开）控制，
> `extract_max_items` 默认 5 → 12，正文上限 60 → 80 字（`_MAX_CONTENT_CHARS` 120 → 160）。

### 9.5 每日上下文重建

这是"每天上下文干净"的落地点。

**关键澄清**：清空短期账本**不会**让 `req.contexts` 变短——原生历史来自 AstrBot 的
`conversation_manager`，是它自己累积的。所以必须显式改写。

| 步骤 | 动作 | 目的 |
| --- | --- | --- |
| 重建 | `conversation_manager.update_conversation(umo, history=[起床提示])` | 每个会话的 history 收缩为"近空白 + 起床提示" |

#### 已确认：取消「固化」

**结论：不做固化。** 即不把当天的 `gated` 消息写进 AstrBot 原生历史。

原因（记录备查）：固化与重建在实现上互相抵消——重建会把 history **整个替换**为
`[起床提示]`，所以只有两种写法：

| 重建时怎么写 history | 结果 |
| --- | --- |
| `history = [起床提示]` | 固化刚写进去的内容被**立刻覆盖**，固化白做 ❌ |
| `history = [起床提示] + gated 消息` | 历史主要由"她没参与过的群聊噪音"构成，比原来还长，与"每天干净"相反 ❌ |

引入 §9.7 的**归档 + `search_history` 后，"跨天不丢"这个目的已被完整覆盖**：
被拦下的消息仍可检索，还不用挤占上下文。而固化的独特价值（让它们成为上下文里的
真实回合）恰恰与"每天干净"直接冲突。

**代价与补偿**：

| 代价 | 补偿 |
| --- | --- |
| 她第二天不会主动记得"昨天群里被拦下的那些话" | 需要时可用 `search_history` 查归档 |
| 她也不主动记得"自己去别的群说过什么" | 同上；且她自己真正在意的内容会经提炼进长期记忆 |

> 这本来也正是"记忆曲线 + 翻聊天记录"这套设计的本意：只记重点，细节按需回查。

- 已核实 `update_conversation(unified_msg_origin, history=[{role, content}, ...])` 存在
  （`astrbot/core/conversation_mgr.py`）
- 重写的是 AstrBot 的**持久化历史**，不是 `req.contexts`；因此**不丢工具调用链与
  多模态图片**——这是相比"接管 `req.contexts` 重建"的关键优势，也不会与天使之心的
  整体覆盖（priority 50）冲突

#### 重建范围：全部已知会话（已确认）

**重建是逐会话操作**，所以必须先定"遍历哪些 umo"。已确认：**全部已知会话都重建**。

| 方案 | 结果 |
| --- | --- |
| 只重建"睡眠期间有新消息的会话" | ❌ **错的**：白天聊得多、夜里没人说话的会话历史照样长，会被漏掉，"每天干净"失效 |
| **全部已知会话** | ✅ 每个会话的 history 都收缩为"近空白 + 起床提示" |

**实现顺序有个坑**：会话列表要从 `short_term_messages` 里 `DISTINCT chat_id` 取，
**必须在清空之前取**——顺序反了就查不到 chat_id 了。

```
1. chat_ids = SELECT DISTINCT chat_id FROM short_term_messages   ← 先取
2. 清空 staged = 0 的行
3. for umo in chat_ids: 重建该会话的历史
```

> 也要说清"重建"的范围：重建的是**会话历史**（`req.contexts` 的来源），
> 长期 / 永久记忆**不重建**——它们正是"每天干净"之后留下的东西。

> 连带提醒：AstrBot 内置的上下文压缩（`agent_runner.config.compression`，默认
> `overflow_strategy=llm_compress`）本就是"溢出时压缩"，与本机制目的重叠。实现前
> 先确认该项当前配置，避免做重。

> 已实现：`MemoryMaintainer` 不管归档与重建（那两步要动账本与 AstrBot 的持久化历史），
> 由 `main._run_curation()` 按 §9.3 的顺序编排，`full_reset` 决定做不做第 8、9 步。
> 重建那一句用 `role="assistant"`——是她自己的记事，写成 user 会被她当成"对方刚说过"。
> 会话列表由 `archive_live()` 在归档**之前**取出来一并返回（顺序写反就再也查不到）。

### 9.6 记忆曲线：清晰度积分

长期记忆不是"要么完整、要么遗忘"，而是随整理**逐级模糊**，越远的越模糊；同时
"被用到"会显著加深它（召回即升级），且这份加深要能顶好几天——否则会出现
"重要的记忆天天被用、却天天被压回去"的痴呆症。

#### 用「清晰度积分」而不是单向等级

单向等级（只降不升）无法表达"升的级要花不只一天抵消"。改用一个可增可减的整数：

```
curation_score   -- 清晰度积分，越高越清晰

新建记忆      score = clarity_full     （默认 4）
每次被召回    score += recall_gain     （默认 3）
每天降级轮    score -= 1               （下限 -1）
```

| 积分区间 | 等级 | 正文形态 | 例 |
| --- | --- | --- | --- |
| `score >= 4` | 0 完整 | 一句话结论（≤60 字） | 「小明上周五说他项目下周三上线」 |
| `2 <= score < 4` | 1 精简 | 保留主语与核心（≤30 字） | 「小明的项目近期上线」 |
| `0 <= score < 2` | 2 关键词 | 只剩检索用关键词 | 「小明 / 项目 / 上线」 |
| `score < 0` | 3 遗忘候选 | 交给 §10 的判据 | — |

`curation_level` **不单独存储**，由 `score` 推导，避免两个字段不同步。

#### 关键：一次召回要能顶 3 天

```
recall_gain = 3，每天降 1   →  一次召回需要 3 天才被抵消   ✓ 不只一天
```

这正是你担心的"痴呆症"防线：被频繁用到的记忆，**召回速度大于降级速度**，会稳定停在
等级 0，永远不会被压缩。反过来，长期没人用的记忆每天掉 1 分，自然滑向关键词级与遗忘。

#### 降级节奏：每天最多一级

整理本身已经是「每晚一次」（§9.1），所以降级天然就是"每天一级"。`demote_interval_hours`
在这里是**护栏**，防止一天内出现两次降级——例如"昨晚 23:59 整理过、今晚 00:01 又整理"
这种跨零点的相邻整理，会把记忆连降两级。

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `demote_interval_hours` | `24` | 距上次降级满这么久才允许再降一级（护栏） |

#### 其他规则

- 降级面向**全部** `tier='long'` 记忆，**不做"弱 / 陈旧"筛选**（按你的要求"整体降"）
- **`source_quote` 原文锚点不随正文精简而改写**——锚点始终指向原文，用于追溯
- 每次降级 `curation_count += 1`，并更新 `last_curated_at`
- `tier='permanent'` 完全不参与

> **整体降级的代价与安全网**：低频高价值记忆（只在生日、忌口这类时刻才用到的）也会
> 每天被降级。安全网有两条：① 用户明确说"记住"的走 `remember` → **永久记忆，不受
> 曲线影响**；② 一旦被召回，`+3` 会把它拉回清晰。所以"重要但罕见"的东西应当走
> `remember`，而不是指望它自己活下来。
>
> 为什么不用概率：积分是**确定性**的加减，每天 -1、召回 +3。可复现、可解释、可日志。

> 已实现：`clarity_full=4` / `recall_gain=3` / 下限 `-1` / 上限 `12` 与 `demote_interval_hours=24`
> 都作为 `core/memory/store.py`、`core/memory/maintenance.py` 的模块常量（§12 未列，避免配置项泛滥）。
> 等级由 `curation_level(score)` 推导，不落库。正文改写按等级：等级 1 交给模型压缩到 30 字，
> 等级 2 直接用检索关键词拼（确定性、零成本），等级 3 保留原正文等 `_forget` 判。
> 单轮重写预算用尽的那批**当晚只降分不改正文**，下一轮会补上（`_fade_body` 带幂等判断）。

### 9.7 模糊记忆的回查通路：自建 `search_history`

按需求设想，"想起某件具体的事"不靠记忆注入，而是**让模型自己翻聊天记录**，和人翻
手机一个道理。

#### AstrBot 内置的 `get_group_message_history` 不够用

`get_group_message_history`（`astrbot/core/tools/message_tools.py`）确实存在，支持
`limit` / `before_id` 分页 / `keyword` / `sender` 过滤，但三个限制使它无法作为主通路：

| 限制 | 说明 |
| --- | --- |
| **仅群聊** | 只在 `GROUP_MESSAGE` 下可用，**私聊没有对应工具** |
| **默认关闭** | 它是 `@builtin_tool(config={"provider_ltm_settings.group_message_history_enable": True})` |
| **滚动窗口** | 由 `group_message_history_max_cnt`（默认 700）决定，**非永久归档** |

**已确认：记忆体系建起来之后不再需要它。** 自建 `search_history` 覆盖了它的全部
用途（且没有上述三个限制），因此不依赖、也不提示用户去开
`provider_ltm_settings.group_message_history_enable`。

#### 已确认：自建一份，覆盖所有会话

**做法：把"清空"改成"归档"，再提供我们自己的查询工具。**

| 项 | 做法 |
| --- | --- |
| 归档 | 不再 `DELETE`，改为给 `staged=0` 的行打上 `archived_at = now`（§13.3） |
| 隔离 | 所有常规查询（`recent_of_chat` / `_context_rows` / `pending` / `build_recent_block` / 记忆页面）一律加 `archived_at = 0` 条件 |
| 工具 | 新增 `search_history(session, keyword, days, limit)`：按会话 + 关键词 + 时间范围查归档 |

这样处理的好处：

- **"每天上下文干净"依然成立**——归档不进上下文、不进注入、不进巡检
- **私聊与群聊一视同仁**——不依赖 AstrBot 的 `group_message_history_enable` 开关
- 顺带修掉一个既有问题：我们自己的 `peek_session` 读短期账本，账本归档后它只能看到
  当天，确实无法承担"翻昨天记录"的职责，现在由 `search_history` 接管

> **语义精确化**：「整理完短期记忆为空」应理解为「**从常规查询与上下文中排除**」，
> 数据保留在归档层。否则某天想回溯会发现数据真的没了——这条很容易做错。

#### 设计要点（避免归档变成第二个"什么都记"的负担）

- 工具只在模型**主动**想确认某件旧事时调用，**不做自动注入**，不参与 `recall()` 打分
- 默认只查**当前会话**；跨会话检索需要显式指定 `session`
- 返回条数受 `limit` 约束（默认 20），按时间正序，便于模型读懂
- 归档保留期由 `archive_retention_days` 控制（**已确认 90 天**），到期才物理删除

> 已实现（v1.4.0）：`search_history` 工具已上线，翻查范围包含当天活着的消息、
> 已清空与已压进摘要的行（唯一排除睡眠期暂存），默认只查当前会话。
> 见 [P6/P7 收尾计划](20261017_P6P7_历史回查与作息收尾计划.md)。

### 9.8 积分与计数字段

与 §9.6 绑定的两个字段：

| 字段 | 含义 | 变化时机 |
| --- | --- | --- |
| `curation_score` | 清晰度积分（等级由它推导） | 新建 = `clarity_full`；召回 `+recall_gain`；每轮降级 `-1` |
| `curation_count` | 累计被降级的次数 | 每轮降级 `+1` |

`last_curated_at` 记录上次降级时刻，用于 `demote_interval_hours` 的节拍判断。
`tier='permanent'` 不参与任何一项。

## 10. 长期记忆遗忘：确定性阶梯

在 §9.6 的记忆曲线之上，遗忘是阶梯的最后一级，**仍然确定性、不用概率**。

替换现有 [`_forget()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/maintenance.py#L124-L131)
的单一阈值判据。

### 10.1 判据

**三条件同时满足**才遗忘：

```
curation_score < 0                                   # 已滑到遗忘候选（等级 3）
AND curation_count >= forget_min_curations           # 至少经历过这么多轮降级
AND now - activity_at() >= forget_stale_days*86400   # 期间始终没被召回
```

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `forget_min_curations` | `6` | 至少经历过这么多轮降级 |
| `forget_stale_days` | `7` | 连续这么多天未被召回 |
| `forget_threshold` | `0.6` | 沿用现有配置，作为强度护栏 |

`activity_at()` 已存在（[store.py](file:///e:/Project/Astrbot/astrbot_plugin_shittim/core/memory/store.py#L102-L104)），
取 `last_recalled_at or created_at`。

### 10.2 为什么不用概率

- **不可复现**：无法回答"这条为什么没了"，只能答"运气不好"
- **系统性伤害低频高价值记忆**：只说过一次的生日、忌口天生就是孤条目、强度低，
  在"精简为主"的整理里最容易被挑中，再叠加概率必然被误删
- **与现有机制冲突**：`_decay()` + `forget_threshold` 已经是确定性遗忘，再加一条
  概率删除，同一条记忆会被两套规则同时判死，行为无法解释

记忆曲线 + 阶梯判据保留了「整理次数」这个你要的信号，只是把它当**陈旧度阶梯**而非骰子。

### 10.3 「被明确要求遗忘」

按需求描述的流程实现（**主流程，不做改动**）：

| 步骤 | 动作 | 对应原描述 |
| --- | --- | --- |
| 1 | `tier` 由 `permanent` 降为 `long` | 「从永久记忆移动到短期记忆」 |
| 2 | 置 `forget_requested = 1` | 「标明被要求忘记」 |
| 3 | `strength` 压到最低（低于 `forget_threshold`） | 让它进入遗忘候选 |
| 4 | 下一轮整理时由 §10.1 的确定性阶梯判据删除 | 「在短期记忆的整理过程中被彻底遗忘」 |

因为强度必定低于阈值、且整理次数会随即达标，第 4 步的删除是**确定性**的，不会
退化成概率行为——这与你在 §2 选定的判据一致。

**配套要求**：§10.3 的降级记忆必须**立刻**从召回候选中排除，否则她会在"已被要求
忘记"到"下次整理"之间的窗口里又把这件事说出来。实现为 `recall()` / `_rank_user_memories()`
里过滤 `forget_requested = 1`，物理删除仍留给整理管线。

> 已知风险（保留原设计，仅记录）：把用户最高优先级的删除意图做成"降级 → 等下次
> 整理淘汰"，意味着它最快也要等到下一个整理周期才真正消失。缓解手段就是上面的
> "立即从召回中排除"，这样流程不变、也不会在中间窗口里被重新提起。

> 已实现：新增 `forget` LLM 工具（按关键词定位最匹配的一条 → `request_forget()`）。
> `request_forget` 把 tier 拉回 long、置 `forget_requested=1`、强度压到阈值一半、
> 积分压到下限，并写入 `suppressed`。`_forget()` 对这类记忆**不等陈旧度**，下一轮
> 整理直接删除并记日志；`recall()` 的两条通道与 `_candidates_by_keywords` 都立即
> 过滤 `forget_requested = 1`。

### 10.4 「被要求遗忘」的新增字段

`memories` 表新增：

```
forget_requested INTEGER NOT NULL DEFAULT 0    -- 被明确要求忘记，立即停止召回
forget_requested_at REAL NOT NULL DEFAULT 0    -- 请求时刻，便于排障
```

## 14. 调度器与生命周期

现有插件是**纯事件驱动**的，没有后台定时器（`_MAINTENANCE_FALLBACK_SECONDS` 也是
挂在"消息发送后"这个事件上）。作息状态机需要真正的周期任务：

- 新增一个 `asyncio` 周期任务（默认 60 秒 tick），负责：
  1. 跨过 `sleep_at` → **入睡收口**（§4.4：撤销焦点、清零信号、写 `sleep_state`）
  2. 跨过 `wake_at` → **起床收口**（§7.1：置 `wake_notice_pending`、把
     `staged` 置 0、touch 睡眠期有消息的会话）
  3. `DEEP` 且 `last_curation_at < sleep_at`（本轮深睡窗口里还没整理过）→ 触发整理（§9.1）
  4. 距 `last_curation_at` ≥ `curation_force_after_hours` 且**不在** `DEEP`
     → 触发兜底整理（只做整理类步骤，**不清空、不重建**）
  5. 跨过自然日 → 重置 `postponed_hours`，按新一天的基础时间表重算
- 任务通过现有 [`self._spawn()`](file:///e:/Project/Astrbot/astrbot_plugin_shittim/main.py#L1245-L1251)
  登记，`terminate()` 里随其它后台任务一起取消
- 每个 tick 后与所有 `await` 之后都要检查 `self._is_terminating`
- 睡眠门是热路径，**不得**在门里做 IO；tick 只更新内存中的状态快照，门读快照

## 15. 技术约束与风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 主动唤醒会绕过 `on_llm_request` | 官方 `active_agent` cron 通路能主动唤醒主脑，但它不经 pipeline：记忆注入、内置工具摘除、发言记账三处全部不生效 | 本期不用该通路，起床回复走「给信息 + 给焦点」（§7.3 方案 A） |
| 睡眠期消息撑爆上下文 | `merge_missing_into_contexts` 无 token 预算 | `staged=1` 的消息不参与合并，起床提示块带预算（§6.3） |
| 注入块重复出现 | 注入块每轮重建 | 持久化 `wake_notice_pending`，注入即清（§7.2） |
| 与天使之心抢占 `req.contexts` | 天使之心在 50 整体覆盖 contexts | 本插件注入在 -10 执行，已晚于它；起床提示 append 在其后（§7.2） |
| 重启后状态错乱 | 纯内存状态无法恢复 | 状态由时间轴推导，不恢复中间态，只持久化 `sleep_at`/`wake_at` 等事实（§3.2、§13.1） |
| 睡眠导致记忆永不整理 | 若她整晚清醒就进不了 DEEP | 保留 24h 兜底维护，两者共用同一入口（§9.1） |
| `sleep_at` 跨自然日 | 23:30 入睡、07:00 起床跨越日期 | `plan_date` 以**入睡日**为基准，判定窗口用时间戳比较而非日期比较 |
| **归档排除条件漏加** | 归档行若没被 `archived_at = 0` 挡住，会重新出现在上下文/巡检/提炼里，"每天干净"静默失效 | 所有查询统一走 `short_term` 的封装方法，禁止业务层直写 SQL；并加回归测试（§16） |
| **未提炼就归档会丢记忆** | 归档排除了常规查询，未提炼的消息将永远进不了长期记忆（虽仍可 `search_history` 查到，但不会"记住"） | 未配提炼模型（`extractor.available == False`）或提炼未清空 pending 时，**禁止归档与重建** |
| **重写原生历史影响面大** | 直接改 AstrBot 的持久化数据，出错会影响所有会话的连续性 | `rebuild_native_history` 独立开关；灰度方式是**先只清账本、不重建**（`rebuild_native_history=false`），确认无误再开 |
| **精简可能把内容改错** | 降级靠模型重写正文，与"禁止引入新信息"的既有约束不同（是压缩而非合并） | `source_quote` 锚点**不改写**，永远可回溯；单次降级条数上限 `curate_max_per_run` |
| 分级覆盖会推高注入量 | 提炼覆盖扩大后长期记忆条目变多 | 靠 §9.6 记忆曲线逐级压缩；两者必须同时上线，否则注入预算会被吃光 |

## 16. 测试点

按项目规范在容器内验证（`docker ps` 确认存在 `astrbot`）：

**状态推导（纯函数，重点覆盖）**
- 睡眠窗口外 → `AWAKE`；`[sleep_at, wake_at-2h)` 且未满 2h → `LIGHT`
- 满 2h → `DEEP`；`[wake_at-2h, wake_at)` → `LIGHT`（即使之前是 DEEP）
- 跨自然日的窗口（23:30 → 07:00）判定正确
- 推迟后 `wake_at` 顺延且不越过 `wake_latest`
- 宽限期内 → `AWAKE`；宽限过期后落回时间轴推导结果

**拦放**
- `LIGHT`：未达阈值 → 事件被 `stop_event()`，且**没有**任何模型调用
- `LIGHT`：达到阈值 → 放行，`focus` 被 touch，宽限被设置
- `DEEP`：@ 与私聊都被拦下，计数不增加，`DEEP` 下永远不产生宽限
- 命令放行：`LIGHT` 与 `DEEP` 下 `/` 指令都能穿透；放行后状态**未**改变、宽限**未**开启
- `AWAKE`：行为与改动前完全一致（回归）

**消息处理**
- 睡眠期消息入账为 `source='sleep'` 且 `staged=1`
- 睡眠期消息**不**刷新焦点；起床后睡眠期有消息的会话才获得焦点
- 睡眠期消息**不**被 `merge_missing_into_contexts` 合并
- 起床提示只注入一次；`wake_notice_pending` 被清除

**记忆整理（节拍与曲线）**
- 触发：同一 `DEEP` 期内只整理一次（`last_curation_at < sleep_at`）
- 兜底：非 `DEEP` 且距上次 ≥ `curation_force_after_hours` 时触发，且**不清空、不重建**
- 提炼循环：`pending` 未清空时继续提炼；触顶仍有积压则**跳过清空**并告警
- 只提炼 `source='live'`；睡眠期消息不被本步骤处理
- 清晰度：每次召回 `+recall_gain`，每轮降级 `-1`，等级由 `score` 推导
- 一次召回后至少需要 3 轮降级才回到原等级（抗"痴呆症"）
- 遗忘判据：`score < 0` + 降级次数达标 + 连续 N 天未召回，三条同时满足才遗忘
- `tier='permanent'` 不参与降级与遗忘
- 深睡整理复用 `extract()` + `merge()`，未引入第三个 prompt 入口
- 提高覆盖后的提炼仍强制 `source_quote` 锚点校验；锚点不随正文精简而改写
- `suppressed` 命中时，提炼不会把已遗忘的内容重新写回

**每日重建与归档（新增，风险最高，需重点覆盖）**
- **硬保护**：`extractor.available == False` 时，归档与重建**都不执行**，且有告警
- 归档只作用于 `staged = 0` 的行；睡眠期消息不受影响
- 睡眠期消息起床时 `staged` 置 0，且 `source='sleep'` 标记保留
- 归档后：`recent_of_chat` / `_context_rows` / `pending` / 记忆页面都**看不到**归档行
- `search_history` 能查到归档行；默认只查当前会话，`limit` 生效
- 归档行**不参与** `recall()` 打分，也不进上下文注入
- 原生历史被重建为「近空白 + 起床提示」，重建后该会话的 history 明显变短
- 重建遍历**全部已知会话**（含当天没有新消息的）
- 重建只改 AstrBot 持久化历史，**不影响** `req.contexts` 的工具链与多模态图片
- 注入顺序为四段式：永久 → 长期 → 短期 → 起床提示（§7.4）

- `python -m compileall -q .`
- `python -c "import astrbot_plugin_shittim.main"`
- `_conf_schema.json` 与 i18n JSON 可被 `json.load` 解析
- 旧库升级：`SCHEMA_VERSION` 6 → 7 后 `memories` 补列、`sleep_state` 建表
